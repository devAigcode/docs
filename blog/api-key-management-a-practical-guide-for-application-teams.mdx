API key management is the operating practice of knowing which credentials your application uses, who owns them, where they are stored, and how they can be replaced safely. For small product teams, it is easy to treat keys as setup details: a value copied into a dashboard, a deployment setting, or a local file. That approach becomes fragile once an application connects to payments, email, analytics, storage, AI services, or other third-party systems.

A practical program does not require a large security team. It requires a clear inventory, limited access, separate environments, a repeatable rotation process, and a response plan for accidental exposure. The goal is to make credential management part of normal application delivery rather than an emergency task.

## Understand API key risks and responsibilities

**Start by treating every API key as a credential with a defined scope and owner.** An API key is commonly used by one service to identify and authorize an application or workload when it calls another service. Depending on the provider and its configuration, a key may permit actions such as reading data, sending requests, creating records, or consuming a paid service.

The risk is not only that a key appears in a public repository. A key can also be exposed through a copied configuration file, a build log, a support ticket, a browser bundle, or an overly broad deployment setting. Even a key that is not public can create operational risk when no one knows what it powers or who can revoke it.

Begin by separating the responsibilities around each credential:

1. **The service owner** decides why the integration exists and whether it is still needed.
2. **The technical owner** understands where the application reads the key and how a replacement is deployed.
3. **The access owner** controls who can view, create, or revoke the key in the third-party provider.
4. **The incident owner** coordinates the response if the credential may be exposed.

In a very small team, one person may fill several roles. The important point is that the roles are named, not that they are held by different people. A key without an owner tends to remain active long after its original integration changes.

It is also useful to distinguish between public identifiers and secrets. Some providers issue values intended for use in client-side code, often with restrictions. Other values are private credentials and must never reach a browser or mobile app package. Do not rely on a variable name alone to make that distinction. Confirm the provider's intended use and the permissions attached to the credential.

## Create an inventory for API key management

**Build a small, maintained inventory before changing storage or rotation practices.** A list of keys gives the team a starting point for reducing unnecessary access and responding quickly when a problem occurs. The inventory should describe credentials without recording the secret value itself.

A spreadsheet, internal document, or secure team system can work if it is kept current. For every key, record:

- the provider and integration it supports;
- the application, service, or job that uses it;
- the environment where it is used, such as development, staging, or production;
- the technical and business owner;
- its permissions or intended scope, where known;
- the storage location and deployment path;
- the date it was created or last reviewed; and
- the replacement and revocation procedure.

Use a distinct credential for each meaningful boundary. Development and production should not share one key. Likewise, an asynchronous worker should generally not need the same credential as a web application if the provider allows separate keys. Separation limits the blast radius of a mistake and makes usage easier to trace.

Next, review the inventory with a removal mindset. Disable or revoke keys for retired experiments, inactive environments, former contractors, and integrations that have been replaced. Before revoking a key, confirm that it is not still used by a scheduled task, a background process, or a separate deployment. The inventory is most valuable when it captures these less visible dependencies.

Avoid using a single shared team credential simply because it is convenient. Shared credentials make accountability and replacement harder, particularly when access needs change. Where a provider supports scoped keys, select only the capabilities required by that application component. If scope cannot be limited, compensate by restricting who can access the key and keeping its use isolated.

## Store and use keys safely

<Frame caption="Private keys should move through controlled deployment configuration to server-side code, not through a repository or browser bundle.">

**Keep secret values outside committed source code and pass them to the application only where they are needed.** This is the foundation of API key security. A `.env` file may be appropriate for local development when it is excluded from version control, but it is not a substitute for controlled production secret management.

Before implementation, make sure you have a few prerequisites in place: an inventory entry for the integration, separate credentials for relevant environments, a way to configure secrets in your deployment environment, and a named person who can administer the provider account. You should also know whether the key is server-only or specifically intended for client use.

Follow these steps when adding a new integration:

1. **Create the key for one purpose and environment.** Name it so its intended workload is recognizable in the provider dashboard. Do not reuse a personal key or a production credential for local experimentation. 2. **Put the value in the approved secret store or deployment configuration.** Use environment variables only as a delivery mechanism; they still need access controls at the hosting, CI/CD, or runtime layer. 3.

Environment variables are widely used because they separate configuration from source code, but they have limits. Anyone with broad access to deployment settings, process inspection, or logs may still be able to view them. Treat the surrounding platform permissions as part of secret management. Review who can change deployment variables, trigger builds, download configuration, or access production shells.

Teams using an application builder should apply the same boundary after generation and export. Review the resulting integration paths before deployment, especially when an API call is initiated from a user-facing feature.

## Set rotation and incident procedures

<Frame caption="Key rotation is a controlled replacement sequence that verifies the new credential before the old one is revoked.">
  ![Rotation workflow diagram showing a replacement API key being deployed, verified, and replacing an old revoked key](/images/blog/api-key-management-a-practical-guide-for-application-teams/inline-2.png)
</Frame>

**Define replacement steps while the current key still works, so rotation does not become an outage.** API key rotation means replacing a credential with a new one and retiring the old value after dependent systems have moved. It reduces reliance on a long-lived secret and provides a practiced path when a key is suspected to be compromised.

There is no single rotation interval that fits every provider or application. Set a schedule based on the key's permissions, exposure, provider capabilities, operational cost, and the team's ability to replace it safely. Higher-risk credentials may warrant more frequent review. A lower-risk integration may be reviewed on a different cadence. The critical requirement is that the decision is explicit and recorded.

A safe rotation procedure usually looks like this:

1. Create a replacement key with the same or narrower required permissions.
2. Add the new value to the relevant secret store or environment configuration.
3. Deploy or restart the workload that uses it, following your normal release process.
4. Verify the intended integration still works without exposing secret values in logs.
5. Revoke the former key after confirming no remaining workload depends on it.
6. Update the inventory with the review date, new identifier if applicable, and any implementation notes.

Some providers allow two credentials to be active during a transition; others may require a more carefully scheduled swap. Design the procedure around the provider's actual behavior rather than assuming overlap is available.

If a key is exposed, act first to contain access. Revoke or disable the affected credential when possible, create a replacement, and update the consuming application. Then determine where exposure occurred: source history, a log, a copied file, a browser request, or an access-control issue. Check the integration's activity using the provider's available records, and remove the exposed value from the location that leaked it.

Capture what changed in a short incident note. This is not about assigning blame. It helps the team improve a control, such as repository scanning, review guidance, or tighter deployment permissions, before the same failure mode recurs.

## Build credential checks into delivery workflows

**Make credential review a release habit rather than a separate security project.** The most dependable controls are the ones that fit into work the team already performs: planning integrations, reviewing code, deploying environments, and offboarding access.

Add a short credential check to pull requests and deployment reviews. The reviewer should ask whether a new third-party service needs a new inventory entry, whether a private key stays server-side, whether the correct environment variable is configured, and whether the required permissions are limited. These questions are brief, but they catch common mistakes before a release.

Use secret scanning where it is available in your code hosting and development workflow. Scanning is a useful safeguard for accidental commits, but it does not replace access controls or key rotation. It may not recognize every provider format, and it cannot address a credential shared through another channel. Treat it as one layer in a broader API key security process.

Access reviews should also cover people and automation. Remove provider and deployment access when a contributor no longer needs it. Check that CI/CD systems have only the credentials required for their jobs, and avoid copying production secrets into preview or test environments without a clear need. When an integration is changed or removed, update the inventory in the same work item.

## FAQ

### What is API key management?

API key management is the process of creating, storing, assigning, monitoring, rotating, and revoking API credentials. It gives a team visibility into what each key can access and a controlled way to replace it when requirements or risks change.

### Should API keys be stored in source code?

Private API keys should not be stored in committed source code. Keep them in a controlled secret store or deployment configuration and have server-side code read them at runtime. A local environment file can be useful for development when it is excluded from version control and access is limited.

### How often should API keys be rotated?

Choose a documented review and rotation schedule based on the key's permissions, provider behavior, exposure, and operational impact. Rotate immediately when a credential may have been exposed, access changes materially, or an integration owner cannot account for its use.

### What should you do if an API key is exposed?

Disable or revoke the key, create and deploy a replacement, investigate the exposure path, and remove the leaked value from the source location. Review available provider activity and record the incident so the team can strengthen the control that failed.

## Conclusion

**Treat API key management as an ordinary engineering control with clear ownership and repeatable steps.** Start with an inventory, keep secret values out of source code, separate environments, and practice key replacement before an incident forces the issue. Small teams do not need a complex program to improve credential management; they need a process that remains usable as integrations and deployments multiply.
