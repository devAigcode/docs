In January 2026, Daniel Stenberg did something no open-source maintainer wants to do: he shut down cURL's bug bounty program after six years. Not because the money ran out. Because AI-generated vulnerability reports had flooded the queue with so much plausible-sounding noise that real security researchers could no longer be heard over it. One of the most battle-tested codebases on the internet — software running on billions of devices — closed its front door because the slop got too deep.

That story is a small window into a much larger problem the industry has started calling **"vibe slop"** — and if you're building software with AI in 2026, it's a problem you're already living with, whether you've named it or not.

## From Word of the Year to warning label

The timeline is almost comically fast. Andrej Karpathy coined "vibe coding" in early 2025: describe what you want in plain English, let the AI write the software, don't sweat the details. By the end of that year, Collins Dictionary had named it Word of the Year. Weekend demos went viral. One-person startups claimed they were shipping production apps solo. The friction between idea and implementation seemed, finally, gone.

Then 2026 arrived, and the term picked up an ugly sibling. Mario Zechner and Armin Ronacher — the engineers behind OpenClaw, one of the most popular autonomous agents of the year — started publicly warning about "vibe slop": codebases that were fast to produce, expensive to maintain, and potentially dangerous to run. The word is a fusion of "vibe coding" and "AI slop," the flood of low-quality generated content clogging the internet. Their argument was blunt: this isn't a tooling quirk, it's a structural risk that will decide which companies survive the next few years.

RedMonk analyst Kate Holterhoff gave the phenomenon an even blunter name: "AI Slopageddon."

## What the security data actually says

The most sobering research of the past year comes from security firms auditing real AI-generated applications, not toy benchmarks:

- **Veracode** tested over 100 large language models on security-sensitive coding tasks. **45% of AI-generated code samples introduced OWASP Top 10 vulnerabilities.** Worse: that failure rate stayed flat from 2025 through early 2026, across multiple testing cycles, even as the same models kept climbing coding leaderboards like HumanEval. Bigger models did not produce safer code. 86% of samples failed to defend against cross-site scripting; 88% were vulnerable to log injection.
- **CodeRabbit** compared thousands of repositories and found AI-generated pull requests carry a **2.74x higher vulnerability rate** than human-written ones.
- **Georgia Tech's Vibe Security Radar** tracked CVEs formally attributable to AI coding tools: 6 in January 2026, 15 in February, 35 in March — and researchers estimate the real count is 5–10x higher, because most AI tools leave no commit metadata to trace.
- **Cloud Security Alliance** research found AI-assisted commits expose hardcoded secrets at **more than twice the rate** of human-only commits — 3.2% versus 1.5%.
- **Wiz Research** found roughly **1 in 5 organizations** using vibe-coding platforms face systemic risks: client-side auth bypasses, hardcoded API keys, insecure database access, exposed internal apps.

Notice the pattern in that last finding. Auth bypasses. Exposed databases. Leaked keys. These aren't exotic zero-days. They're the boring, load-bearing parts of an application — authentication, authorization, data access, secrets management — the exact parts a vibe-coded demo skips because they don't show up in a screen recording.

## Why the models can't fix this alone

There's a tempting assumption buried in every "just wait for the next model" argument: that code security is a capability problem, and capability is rising, so the problem will solve itself.

The Veracode data refutes it directly. Between 2025 and early 2026, coding benchmark scores rose steadily while the security pass rate sat frozen at roughly 55%. Larger models did not outperform smaller ones on security. The explanation is structural: models are trained to produce code that *works*, and the internet's corpus of working code is riddled with the same twenty-year-old vulnerability patterns human developers slowly learned to avoid. The model reproduces what it saw. It saw a lot of SQL string concatenation.

There's a human factor too, and it has a name: **automation bias** — the tendency to trust output simply because a machine produces it. When code arrives instantly, formatted beautifully, with confident comments, reviewing it feels like paranoia. The Zechner–Ronacher warning centers on exactly this: the danger isn't that AI writes bad code sometimes; it's that AI writes *plausible* code always, and plausibility switches off human skepticism.

Meanwhile, new attack classes have emerged that only exist *because* of AI coding tools. "Slopsquatting" — attackers registering the package names AI models hallucinate, so your `npm install` pulls malware the AI confidently recommended. The "Rules File Backdoor" — poisoning the configuration files coding agents read as instructions. Neither has a precise analog in traditional secure development guidance. The attack surface didn't just grow; it mutated.

## The real lesson: the constraint moved

So should you stop using AI to build software? That would be the wrong conclusion — and, judging by the 92% daily adoption number, nobody's going to draw it anyway.

The right conclusion is subtler. As one 2026 analysis put it: **generating plausible code is now cheap; generating correct, secure, maintainable code is not — and the gap between those two is where technical debt accumulates and security incidents originate.** The constraint on building software has moved from *writing code* to *everything around the code*: architecture, authentication, data integrity, secrets handling, deployment, review.

Look back at the audit findings and a picture emerges of where vibe slop actually lives:

1. **Auth and permissions** — client-side auth checks, missing role enforcement, everyone-is-admin defaults.
2. **Data layer** — insecure direct database access, no migrations, schema drift between what the AI generated last Tuesday and this Friday.
3. **Secrets** — API keys pasted into source at twice the human rate.
4. **Deployment** — apps that ran on `localhost`, pushed to production with debug flags on and internal endpoints exposed.

None of these are "code quality" in the syntax sense. They're *engineering* — the system-level discipline that a prompt-to-code loop, by construction, has no opinion about.

## Two ways forward (and the one most people should take)

For teams with engineering leadership, the answer is governance: treat AI output as untrusted input, require human review at production boundaries, enforce test and security gates before deploy. That's what the organizations avoiding these outcomes actually do — they didn't abandon vibe coding, they caged it.

But that answer quietly assumes you *have* a security review process, a CI pipeline, and someone who knows what an OWASP Top 10 is. Most of the people vibe coding in 2026 — founders, indie hackers, small business owners building their own tools — don't. ## The takeaway

"Vibe slop" isn't a verdict on AI-assisted development.
